### Ключевые моменты схемы:

- API Layer — только получение запросов, валидация через Pydantic schemas.

- Services — оркестратор: берёт данные из репозиториев, создаёт агрегаты, вызывает методы агрегатов.

- Aggregates — управляют инвариантами и бизнес-правилами, принимают данные через DTO/словарь.

- Repositories — контракт в domain, реализация в infrastructure, знают как сохранить/получить данные из конкретной БД или кэша.

- Infrastructure — все внешние системы: БД, Redis, MinIO, Celery.

## ⚡ Основные принципы архитектуры

### 1. API Layer
- Только **эндпоинты и схемы (Pydantic)**.
- Принимает запросы, валидация через schemas.
- Не содержит бизнес-логики.

### 2. Services (Оркестратор)
- Получает данные из **репозиториев**.
- Создаёт **агрегаты домена** и вызывает их методы.
- После изменений агрегата — сохраняет данные обратно через репозитории.
- Управляет **транзакциями**, оркеструет операции внутри одной транзакции.

### 3. Domain Layer
- **Aggregates**: Product, Sale, Operations, Employee.  
  - Управляют состоянием, проверяют **инварианты**, создают события.
- **DTO**: отдельные dataclass для передачи данных между слоями.  
  - Позволяют автокомплит и проверку типов.
- **Repositories (контракты)**: определяют интерфейс хранения/получения данных.
- **Access**: политики и исключения доступа (RBAC).

### 4. Repositories
- Интерфейсы в **domain/repositories**.
- Реализация в **infrastructure** (Postgres, Redis, MinIO и т.д.).
- Принимают DTO/объекты агрегата для сохранения.
- Могут содержать сложные SQL-запросы для отчётов или аналитики.

### 5. Infrastructure
- Внешние системы: **БД, кэш, хранилище, таски (Celery)**.
- JWT, Redis, MinIO — отдельные модули с `config.py` и клиентом.

## 🌀 Поток данных при операции

1. API → сервис:
   - Валидация через Pydantic.
2. Сервис:
   - Запрашивает DTO из репозитория.
   - Создаёт агрегат, передаёт DTO.
   - Вызывает методы агрегата (изменение состояния, проверка инвариантов).
3. Агрегат:
   - Изменяет внутреннее состояние.
   - Генерирует события (опционально).
   - Возвращает DTO обратно.
4. Сервис:
   - Получает DTO/агрегат.
   - Передаёт в репозиторий для сохранения.
5. Репозиторий → Infrastructure:
   - Сохраняет в Postgres/Redis/MinIO.

## ✅ Ключевые решения

- Все **агрегаты домена** не знают о внешних системах.  
- **DTO** используется для типизации и передачи данных.  
- **Сервис** — единственная точка, которая дергает репозитории и агрегаты.  
- **Operations** — отдельные агрегаты для каждой операции (sale, sale_return, etc.).  
- **Transactions** — агрегируют несколько операций, чтобы обеспечить атомарность.  
- Миграции и тесты лежат снаружи `src` для удобства CI/CD и запуска.  
- Внутренние исключения для приложения реализуются через `dataclass` с `slots=True` и `frozen=True` для лёгкости и иммутабельности.

---

> Архитектура ориентирована на **чистый домен, оркестрацию через сервисы и изоляцию инфраструктуры**, с балансом удобства разработки и типизации через DTO.
